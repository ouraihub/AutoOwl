# 工程规范与质量门禁

版本：v1（2026-08-18）  
前置阅读：`概要设计.md`、`详细设计.md`、`音源与已知问题.md`

本文档是可执行约束，不是建议。每条规则必须有自动检查、测试或 code review 依据。没有验收证据的代码不得标记为完成。

## 1. 强制架构边界

```text
Svelte route/page
    -> typed service
    -> Tauri command/event
    -> application use case
    -> domain trait
    -> infrastructure adapter
```

| 边界 | 强制规则 | 检查方式 |
|---|---|---|
| 页面/组件 -> IPC | 不得直接调用 `invoke`，必须经 `$lib/services` typed service | ESLint `no-restricted-imports` + review |
| 业务组件 | 只接收 props 并通过 callback/event 输出，不自行取数 | review + 组件测试 |
| domain | 不得依赖 Svelte、Tauri、SQLite、HTTP 或具体平台 | 目录依赖检查 + review |
| Tauri command | 只做 DTO 校验、权限检查和 use case 调用，不写业务编排 | review；超过 20 行必须说明原因或拆分 |
| application | 只依赖 domain 抽象，不依赖具体音乐源、SQLite 或 Tauri API | review + fake adapter 测试 |
| infrastructure | HTTP、SQLite、文件、FFmpeg、Cookie 和平台差异只能放在 adapter | review + 集成测试 |
| 音乐源 | 不得在共享流程散落 `if source == ...`，平台差异只能在 source adapter | adapter contract test + review |
| 系统能力 | 进程、路径、通知、外部链接和凭据只由 Rust adapter 访问 | capability 审查 + review |

## 2. 接口优先和测试替身

以下抽象必须是 Rust trait，并至少有一个测试替身：

| 抽象 | 测试替身 | 禁止行为 |
|---|---|---|
| `MusicSource` | `FakeMusicSource` | application 直接调用平台函数 |
| `DownloadService` | `FakeDownloader` | 测试直接访问真实下载站点 |
| `PlaybackResolver` | `FakeResolver` | player 直接拼接平台 URL |
| `CredentialStore` | `MemoryCredentialStore` | 测试写真实 Cookie |
| `FileSystem` | `TempFileSystem` | domain 直接调用 `std::fs` |
| `MediaTool` | `FakeMediaTool` | 测试强制安装 FFmpeg |
| `HttpClient` | `MockHttpClient` | 单元测试依赖实时网络 |
| `Clock` | `FixedClock` | 测试依赖当前时间 |
| `ProgressSink` | `RecordingSink` | service 直接调用 Tauri emitter |

判据：如果 domain/application 测试必须联网、必须安装 FFmpeg、必须写用户目录或必须启动 WebView，说明接口边界不合格。

## 3. Rust 规范

- 开启 `rustfmt`、Clippy 和编译器警告；CI 使用 `-D warnings`。
- 生产代码禁止 `unwrap()`、`expect()`、`panic!()`、`todo!()` 和 `unimplemented!()`。
- 生产错误不得使用 `String` 代替错误类型；使用 `thiserror` 分层定义错误。
- 公开跨模块类型使用明确 DTO、enum、值对象和 trait；模块默认使用 `pub(crate)`。
- 不使用 `static mut`、可变全局单例或隐式全局状态；应用状态统一注入 `AppState`。
- 不在持有 `MutexGuard` 时执行 `.await`、I/O、进程调用或发送事件。
- 长时间阻塞操作使用 `spawn_blocking` 或专用任务；Tauri command 不阻塞 WebView。
- 文件路径、下载文件名、远程响应、Cookie 和外部进程参数必须经过边界校验。
- 所有反直觉的业务分支必须有 `///` 注释说明原因（例如平台接口的特殊行为）。

### 3.1 错误类型

内部错误保留 source chain；跨 Tauri 边界只返回脱敏的 `IpcError`：

```rust
#[derive(Debug, serde::Serialize)]
#[serde(rename_all = "camelCase")]
pub struct IpcError {
    pub code: String,
    pub message: String,
    pub retryable: bool,
    pub operation_id: String,
}
```

禁止把原始 stderr、Cookie、完整播放 URL、绝对路径或第三方响应直接返回前端。

## 4. TypeScript 和 Svelte 5 规范

- `strict` 必须开启；禁止无边界 `any`、空 `catch` 和无理由非空断言 `!`。
- 所有 command 请求、响应和 event payload 都必须有显式 TypeScript 类型，并与 Rust `serde` DTO 对应。
- 跨边界字段使用 `camelCase`；Rust 使用 `#[serde(rename_all = "camelCase")]`。
- Svelte 5 新代码只使用 `$state`、`$derived`、`$effect` 和 snippets，不新增 legacy slot/store 写法。
- 页面负责组合，业务组件负责交互，基础 UI 组件不包含业务判断。
- 组件必须支持 loading、empty、error、retry、disabled 和成功状态。
- 副作用、异步请求和订阅放在 route、service 或 store，不能散落在深层组件。
- 组件不得直接读取 SQLite、文件路径、Cookie 或 Tauri `AppHandle`。
- shadcn-svelte/bits-ui 上游组件不直接修改；需定制时在外层包装。
- 使用 lucide 图标和语义化控件，必须保留键盘操作、焦点、ARIA 和可见焦点。
- 颜色只使用 app.css/Tailwind 语义 token；业务组件不得写死颜色值。

## 5. Tauri 2 规范

- capability 放在 `src-tauri/capabilities/*.json`，按窗口授予，不使用全局通配权限。
- 只启用实际需要的 `core:event`、dialog、notification、限定范围 fs 和 opener 能力。
- 不开放任意 shell、任意路径读写、任意 URL 打开或任意命令执行。
- FFmpeg/ffprobe 只能由 Rust `MediaTool` adapter 以固定参数启动，前端不能启动进程。
- command 使用一个 Request DTO，不使用大量平铺参数。
- command 返回 `Result<T, IpcError>`；函数体只做校验、授权、调用和转换，目标不超过 20 行。
- 长任务 command 立即返回 task DTO，进度通过显式 event 推送；event 丢失后可用 query command 恢复状态。
- event 名称使用稳定的 `scope:changed` 形式，payload 必须有明确版本和类型。
- Tauri plugin 的 Rust crate 和 npm 包必须固定相同 major/minor 版本。
- release 不开放 devtools；Windows 构建必须验证 WebView2、数据目录和权限。

## 6. 使用与管理子系统边界

```text
使用子系统
├── search / collection / player / download
├── local_music / history / lyrics / cover
└── source switching

管理子系统
├── settings / credentials / qr_login
├── media_tools / diagnostics / update
└── capability-sensitive commands
```

- 用户页面只能调用 user service；管理页面只能调用 admin service。
- Cookie、密码、FFmpeg 路径、日志导出和系统能力只能由管理 command 处理。
- 管理命令必须单独做权限和参数校验，不能因为前端隐藏按钮就认为安全。
- 首发是一个 Tauri 应用、一个 Rust core、一个 SQLite；不拆独立后台服务。

## 7. 音乐源和下载门禁

- 每个平台必须实现 `MusicSource`，并登记能力矩阵：歌曲、歌单、专辑、歌词、封面、播放、下载、Cookie、扫码和音质。
- 每个平台必须有 fixture/contract test；真实网站验证单独标记 `verified`、`degraded` 或 `blocked`。
- 公共 domain 不得出现平台私有字段和平台专属分支。
- 下载必须经过 `queued -> resolving -> downloading -> processing -> completed` 状态机。
- 取消、失败和重试必须有明确状态和错误码；临时文件必须清理。
- 目标文件必须使用临时文件完成后的原子移动，禁止直接覆盖写入。
- 文件名模板只允许 `{name}`、`{artist}`、`{album}`、`{source}`、`{id}`、`{ext}`；路径穿越段和非法字符必须清理。
- 下载历史清理不得清除 dedup 记录。

## 8. 数据库和迁移门禁

- 应用使用自己的应用数据目录，不读取、不修改其它程序的数据库、配置或下载目录。
- 每个 schema 版本使用独立迁移文件，并在事务中执行。
- 迁移必须幂等；失败必须整体回滚。
- source、scope、siteId 组成远程内容身份；歌单歌曲关联必须包含 collection、song 和 source。
- 任何删除操作必须定义文件、索引、关联和历史的影响范围。
- 数据库测试使用临时数据库，禁止修改开发者真实数据。

## 9. 日志规范

- 使用 `tracing`/`tracing-subscriber`，不使用散落的 `println!` 或正式环境 `console.log`。
- 日志事件使用稳定 snake_case，动态信息使用结构化字段，不拼接敏感信息。
- 必需字段：时间、级别、模块、事件、operation_id；任务场景增加 task_id、stage、duration_ms。
- 禁止记录 Cookie、密码、Authorization、完整敏感 URL 和用户文件内容。
- 错误日志必须有 error code、操作、可定位上下文和 source chain 摘要。
- 日志按天或大小滚动，默认保留 7 天；日志目录位于应用数据目录，不进仓库。
- 前端只记录用户动作和状态转换，不复制 Rust 原始堆栈。

## 10. 自动化质量门禁

必须提供并通过以下命令：

```powershell
pnpm check
pnpm lint
pnpm test
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test
pnpm build
```

建议提供 `pnpm verify` 串联全部门禁。任何一项失败不得生成发布包。

最低测试要求：

- domain：值对象、状态机、错误映射
- application：用例、重试、取消、事务和权限
- infrastructure：HTTP/SQLite/文件/FFmpeg fake
- interface：command 参数、DTO、event 和错误脱敏
- frontend：service、store、组件交互和页面状态
- source adapter：每个平台 fixture/contract test

## 11. 人工验收门禁

自动化测试不能替代以下验收：

1. 每个平台至少完成一次真实搜索/播放资源/歌词或封面验证，并记录状态。
2. Windows Tauri 开发环境完成搜索、试听、下载、取消、重试、设置和关闭流程。
3. Windows WebView2 媒体键、窗口关闭、外部链接和通知行为完成验证。
4. FFmpeg/ffprobe 存在和缺失两种环境都完成降级验证。
5. 日志导出和诊断信息不包含 Cookie、密码和敏感 URL。
6. `音源与已知问题.md` 中每个已完成项都有代码路径、测试命令和验收证据。

## 12. 大模型工作门禁

每次任务必须遵循：

```text
读取概要设计、详细设计、音源与已知问题和本规范
  -> 阅读相关代码、平台接口样例和测试
  -> 先补接口/DTO/fixture 缺口
  -> 实现最小变更
  -> 执行任务验收和全局门禁
  -> 更新 `音源与已知问题.md` 的状态、证据和遗留问题
```

大模型不得：

- 未取得平台接口样例（fixture 或抓包）就实现 adapter 行为。
- 用兼容别名、临时 shim 或重复实现掩盖契约不一致。
- 把未运行验证的平台能力标记为完成。
- 删除或覆盖用户已有修改。
- 为通过测试修改测试预期而不记录原因。
- 在一个任务中顺手引入无关重构。

## 13. 完成判据

功能只有同时满足以下条件才可标记为 `完成`：

1. 有行为说明（设计文档或代码注释）。
2. 有 domain/application 接口、Rust 实现和 TypeScript DTO。
3. 有 Tauri command/event 和前端 typed service。
4. 有成功、失败、取消或重试路径。
5. 有 fixture、单元测试或集成测试。
6. 有结构化日志和稳定错误码。
7. 有 loading/empty/error/retry/disabled UI 状态。
8. 通过自动化质量门禁。
9. 完成所需的 Windows 或真实平台人工验收。
10. `音源与已知问题.md` 记录完成证据、测试命令和遗留问题说明。

## 14. 规范维护规则

- 新增规则必须同时说明检查方式。
- 规范与 `概要设计.md`、`详细设计.md` 冲突时，先暂停实现并记录 ADR，不自行选择兼容方案。
- 发现同类故障两次以上，必须把 review 约定升级为自动检查或测试。
- 修改本规范时必须更新版本和日期。
